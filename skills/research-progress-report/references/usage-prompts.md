# 推荐使用方式与 Prompt

显式写出 `$research-progress-report` 是最稳定的调用方式。推荐把任务拆成“证据与大纲确认 → 小批量页面确认 → 完整交付”三轮；这样既保留用户对重点和视觉系统的控制，也避免在未确认的叙事上制作整套材料。

## 第一轮：证据台账与大纲

```text
使用 $research-progress-report。

工作目录：<绝对路径>
时间范围：<YYYY-MM-DD> 至 <YYYY-MM-DD 或现在>（Asia/Shanghai）
汇报对象：<导师/课题组/评审；默认不了解项目内部代号>
汇报目的：<周报/阶段汇报/路线决策>
预计时长：<例如 15 分钟>

请先只完成：
1. 可追溯的具体进展台账；
2. 面向陌生听众的任务定义卡；
3. 实验口径映射，区分正式比较、诊断、预检和探索实验；
4. 归并为 3–6 项汇报主线，并标注重点/简报/附录；
5. 列出证据缺口、不可声称内容、待讨论路线和需要我确认的问题；
6. 建议 PPT 页数、汇报时长和前 5 页的页面任务。

先不要制作 PPT，等我确认大纲。
```

## 第二轮：确认视觉与叙事系统

```text
我确认以上大纲。请先制作前 5 页 PPT 供我确认，不使用固定模板，根据本期证据自由设计。

要求：
- 学术汇报风格，中文字体使用微软雅黑；
- 所有可见文字均不小于 16 pt，包括图例、坐标轴、脚注和页码；
- 除封面外，每页安排 2–4 个互相支撑的证据单元；
- 内部实验代号不能承担叙事，只能作为括号内的追溯标签；
- 每个指标首次出现时解释含义和“越高/越低越好”；
- 不同实验口径不得混在同一比较结论里；
- 生成后检查源 PPT 和导出预览，并让一个完全不了解背景的子 agent 冷读；关闭全部 blocker 和 major 后再交付。
```

## 第三轮：扩展完整汇报

```text
前 5 页的叙事、信息密度和视觉风格已确认。请沿用这一套页面系统完成剩余 PPT。

保持已经确认的任务定义、实验口径和重点分级；新增内容必须能追溯到证据台账。完成后再次执行字号、字体、溢出、图表可读性、证据脚注和无背景冷读检查，并交付可编辑 PPTX 与预览文件。
```

## 轻量周报模式

```text
使用 $research-progress-report，对 <目录> 在 <时间范围> 的变化做轻量周报。只输出一页文字摘要：本周完成、最强证据、失败/风险、需要决策、下周最小计划。任何没有结果证据的代码改动只能写成“实现进展”，不能写成科研结论。
```

## 定向修订模式

```text
使用 $research-progress-report 修订这份已有汇报：<PPTX/大纲路径>。
不要重做已确认的主线，只检查并修复：内部代号、任务定义缺口、实验口径混报、低信息密度、字号小于 16 pt、字体不一致，以及冷读审查中的 blocker/major。输出修改清单和新版文件。
```

## Prompt 编写原则

- 固定写清目录、绝对时间范围、汇报对象、汇报目的和预计时长。
- 第一轮只确认事实与主线；第二轮只确认少量页面；确认后再扩展全稿。
- 把“不了解内部代号”写成听众默认条件，而不是等出现看不懂的问题后再补术语表。
- 若项目有测量边界、不可分发数据或 Gate 规则，在 prompt 中要求先读取项目 `AGENTS.md` 和权威研究文档。
- 若只需文字周报，明确说明不制作 PPT，避免触发不必要的载体工作。

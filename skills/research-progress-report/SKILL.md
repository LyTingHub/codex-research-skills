# 科研进展汇报

把“目录与时间范围”转换成一条易讲、可信、可决策的科研汇报主线。默认先交付文字台账与大纲，等待用户确认重点和载体后，再制作成品。

## 调用边界

自动调用必须同时满足两个条件：

1. 用户明确要准备正式汇报载体或汇报结构，例如组会、科研周报、阶段汇报、导师沟通材料、PPT 或汇报网页；
2. 用户给出需要汇总的明确时期，例如起止日期、“本周”“过去两周”或“从某日到现在”。

仅出现“汇报实验进展”“实验进展怎么样”“最新实验结果”“最近在跑什么”等表述时，不使用本 skill。把它们视为实验状态查询：直接查看最近运行、日志、指标和异常，简洁回答当前结果即可，不进入跨时期证据台账、大纲确认或 PPT 制作流程。

若用户明确要做正式组会/周报但没有给时间范围，先询问或确认汇总时期；在时期明确之前不要启动本工作流。用户始终可以通过 `$research-progress-report` 显式调用。

## 必要输入与默认值

- 优先使用用户给出的工作目录和起止时间；“到现在”按当前本地日期解释并在输出中写明绝对日期。
- 用户未指定输出位置时，先在对话中汇报，不写入仓库。
- 用户未指定汇报对象时，按“面向导师/课题组、需要快速理解结果并作出路线决策”组织。
- 只有缺失信息会实质改变证据范围或最终载体时才提问；其余采用合理默认并明确标注。
- 在汇总结果前先建立“任务定义卡”：用陌生听众能理解的语言写清研究输入、目标输出、预测/分析范围、数据或测量来源，以及本周期判断成功与否的标准。找不到证据的字段标为 `Unknown`，不得用项目代号或常识补齐。

## 证据采集

先阅读目标目录内的 `AGENTS.md`、研究流程和权威索引。遵守数据、Git、隐私、不可分发材料与实验协议边界。采集只读证据，除非用户另行授权写入。

围绕时间窗口检查：

- Git 提交、diff 与工作树中的近期改动；
- 实验注册表、配置、日志、聚合指标、图表、manifest 和运行契约；
- 研究笔记、分析文档、handoff、讨论记录和待决策项；
- 文献调研、竞品/基线实现与应用调研；
- 时间窗口内生成但位于仓库外的已登记产物。

修改时间和 handoff 只能用于发现线索，不能单独证明科研结论。不要把未运行代码、计划或文件名写成已完成结果。范围较大时，先列候选证据，再读取最能支撑结论的源文件；不要无差别读取大体积原始数据、checkpoint 或逐窗口表。

将每条主张标为：

- `Observed`：原始或聚合结果直接显示；
- `Derived`：由已注明的方法从 Observed 计算或归纳；
- `Hypothesis`：解释、机制或尚待验证路线；
- `Unknown`：证据不足、冲突或尚未核实。

若目标项目有自己的证据标签或实验协议，以项目规则为准。协议、数据切分、统计单位或指标不可混报；存在口径差异时并列呈现并说明不可直接比较。

在进入汇报主线前建立“实验口径映射”。每项主要结果至少注明：实验角色（正式比较、诊断、预检或探索）、数据集/受试者范围、切分或 fold、样本与统计单位、比较双方、指标含义与方向、证据位置。不同数据规模、切分、统计单位或输入输出定义的结果不得放在同一张横向比较表中，除非明确分区并说明不可直接比较。

## 阶段一：具体进展台账

逐项记录可独立汇报的进展，建议字段见 [进展台账与大纲格式](references/report-schema.md)。每项至少包含：完成了什么、为何重要、证据位置、当前结论、限制/风险、下一步或待决策事项。

先保留细粒度，再聚类。常见聚类包括但不限于：

- baseline/对比方法与定量结果；
- motivation、数据特性与可视化分析；
- 实验结果解读、失败模式和诊断；
- 不同创新点/技术路线及其证据、代价和待确认问题；
- 应用方向调研，包括相关论文、可复现对比方法和需要讨论的后续方案。

不要把同一结果在多个类别重复计为多项进展；可用交叉引用表达它同时支撑哪些论点。

## 阶段二：汇总与汇报主线

把台账压缩为 3–6 个大点，并按照听众做决策的顺序组织，而不是简单按时间排序。默认主线：

1. 本周期要解决的核心问题与判断标准；
2. 已完成的关键工作和最可信结果；
3. 结果说明了什么、还不能说明什么；
4. 候选创新路线的对比与需要导师确认的选择；
5. 应用/外部调研如何改变研究路线；
6. 下一周期行动、依赖与明确的讨论问题。

对每个大点标注汇报权重：

- `重点`：影响核心结论或需要现场讨论/决策，分配主要时间和视觉空间；
- `简报`：证明推进但不需要展开，1–2 句话或一张汇总图；
- `附录`：支持追问与复核，不打断主线。

推荐重点时同时写理由，例如“新发现”“改变路线判断”“证据最强”“需要导师拍板”。汇报结构必须显式列出待讨论问题，不把多条候选路线伪装成已定方案。

## 确认门

先向用户交付：

1. 完整文字版进展台账；
2. 面向陌生听众的任务定义卡和实验口径映射；
3. 聚类后的汇报大纲；
4. `重点 / 简报 / 附录` 建议；
5. 证据缺口、口径冲突和待讨论事项；
6. 建议页数/篇幅与预计汇报时间。

然后等待用户确认或调整大纲，并让用户选择最终载体。未确认前不要制作完整 PPT、网页或正式成稿；用户明确授权直接完成时可自行审核后继续，但仍需保留台账和大纲。

## 阶段三：制作最终载体

- PPT：使用 `ppt-master` 的自由设计流程，把已确认大纲作为内容合同；每次依据本期证据、图表和汇报重点重新设计页面系统。默认采用学术汇报风格、可编辑图表和证据脚注。每页只承担一个清晰的 page job，主结论写成标题或 takeaway，路线比较和实验结果优先可视化。
- 网页：使用 `sites`，将主线、图表、证据与附录组织成可导航的单页或分区页面。
- 文字版：保留结论层、证据层、限制层和决策层，避免把文件清单当正文。

引用本地证据时给出可定位的文件路径，必要时加行号、命令或 artifact ID。不得为了版面整洁删去关键限制，也不得补造不存在的数字、论文结论或导师意见。

### PPT 可读性与信息密度

- 用户未另行指定时，所有可见文字不得小于 16 pt；标题、正文、图例、坐标轴、来源和页码都适用。导出前必须对生成文件逐项检查，不能只检查设计稿中的目标字号。
- 中文学术汇报默认使用微软雅黑（Microsoft YaHei）；用户指定其他字体时以用户要求为准。若制作或预览环境缺少该字体，PPT 主题与文本仍应声明为微软雅黑，并在交付时披露替代渲染情况，不得静默更换后声称字体要求已满足。
- 除封面和必要的章节过渡页外，每页通常应承载 2–4 个互相支撑的证据单元，例如“结果图 + 核心数字 + 解释 + 限制”。信息不足时缩减页数，不用大面积空框、装饰性留白或单句卡片稀释内容。
- 信息密度来自证据组织，不来自缩小字号或堆叠长段落。优先使用带明确结论的图、表、对比矩阵、案例序列和紧凑注释。
- 默认把正文写给“完全不了解项目内部实验编号的科研听众”。内部代号、配置名和缩写不能承担叙事：首次出现时必须改写为它验证的问题或完整含义，例如用“事件预测能力验证”代替 `D1-P`；确需保留代号时，将其降为括号内的追溯标签。指标缩写同样需要给出中文含义和方向说明（如“越低越好”）。
- PPT 或正式文字稿完成初稿后，在可用且获授权的情况下交给一个不继承项目背景的独立子 agent 做冷读审查。只提供成稿及必要的汇报对象说明，不提供实验代号表、预期结论或作者解释；要求它逐页复述“研究问题—证据—结论—限制”，并把问题标为 `blocker / major / minor`：无法识别研究任务、误读核心数字/比较关系、或把限制理解成结论属于 blocker；需要作者口头补充才能串起关键推理属于 major；局部措辞与非关键术语属于 minor。主 agent 必须关闭全部 blocker；major 应关闭，确需保留时必须写明理由和现场补充方式。修改后至少做一次无背景复查或逐项回映，确认问题确实消失，再做最终导出检查。
- 用户要求先看若干页时，只制作该批页面并完成视觉检查；用户确认后再扩展剩余页面，避免把未确认的视觉系统复制到整套汇报。

## 完成检查

- 时间范围与“到现在”的绝对日期已写明；
- 每个重要数字和主张可追溯；
- 观察、推导、假设和未知没有混淆；
- 同协议结果才进入同一对比；
- 任务定义卡和实验口径映射完整，陌生听众无需认识内部代号即可理解研究输入、输出和比较范围；
- 汇报重点与用户需要作出的决策一致；
- 用户确认的大纲与最终载体一致；
- PPT 所有可见文字均达到用户要求的最小字号，且已检查导出文件而非仅检查源稿；
- 正文页没有由空占位框、装饰性留白或重复单句造成的低信息密度；
- 内部代号和指标缩写已展开或改写为陌生听众可理解的问题表述；已完成无背景冷读审查，全部 blocker 已关闭，major 已关闭或有明确保留理由；
- 附录足以支持对方法、口径和失败结果的追问。
